## PROJECT OVERVIEW

MatchIQ is a Final Year Project (FYP) — an AI-powered football (soccer) match analytics
platform. It ingests a raw match video, runs a multi-stage computer vision pipeline to
track players and the ball, computes movement metrics, fatigue scores, goal probabilities,
and match outcome predictions, then serves all results through a FastAPI backend and a
Next.js web dashboard.

The system operates in two modes:
- **Batch/Upload** (main.py / api_server.py upload flow): processes an entire video offline,
  writes CSVs, archives the match.
- **Live/Real-Time** (api_server.py realtime flow): accepts a YouTube/Twitch/streamlink URL,
  resolves the direct stream URL (via streamlink → yt-dlp fallback), captures frames via
  cv2.VideoCapture, processes them through RealTimeTracker, and pushes annotated JPEG frames
  + live positions over the WebSocket to the frontend.


## PROBLEM STATEMENT

Professional football analytics tools (Opta, StatsBomb, etc.) are prohibitively expensive
and unavailable to lower-league clubs, academies, and grassroots teams — particularly in
Pakistan and other developing markets. MatchIQ provides affordable, automated match
analysis from a single video file, requiring no specialised hardware beyond a consumer GPU.

## PIPELINE — DETAILED STAGE-BY-STAGE EXPLANATION

### Phase 1 — Player Tracking  (Player_Track.py)

**Models:**
- `football-vgiqa-3njno/2`  (Roboflow YOLOv8) — detects Ball, Goalkeeper, Player, Referee
- `football-field-detection-f07vi/14` (Roboflow YOLOv8) — detects 32 pitch keypoints

**Models are pre-loaded at startup** (not re-loaded per run):
`api_server.py` starts `_load_models()` in a daemon thread via the FastAPI lifespan
`asynccontextmanager` (replaced the deprecated `@app.on_event("startup")`). Models are
stored as `_player_model` and `_field_model` module globals and a `_models_ready` flag is
set to `True` after loading + a warmup inference (first-inference JIT). `POST /run`
returns HTTP 503 if `_models_ready` is False. The `/status` response now includes
`"models_ready": bool`.

**Tracker — BoxMot HybridSort (switched from OC-SORT):**
The tracker was changed from `trackers.OCSORTTracker` to
`boxmot.trackers.hybridsort.hybridsort.HybridSort`. Both `process_all_frames()` (batch)
and `RealTimeTracker` (real-time) now use HybridSort with:
- `reid_weights=Path(".model_cache/osnet_x0_25_msmt17.pt")` — OSNet Re-ID weights
- `cmc_method='sof'` — sparse optical flow camera-motion compensation (cheap for static cameras)
- `track_thresh=0.3`, `low_thresh=0.1`, `max_age=5000` (batch) / `5000` (RT)
- `min_hits=3` (batch) / `1` (RT), `iou_threshold=0.3`, `delta_t=3`
- `use_byte=True`, `with_reid=True`, `with_longterm_reid=True`
- RealTimeTracker uses `half=True` (FP16) for faster GPU inference
- RealTimeTracker label annotator uses `text_scale=0.4, text_thickness=1` (smaller text)

**BoxMot bridge helpers in Player_Track.py:**
- `_sv_to_boxmot(sv.Detections) → np.ndarray` — converts supervision Detections to
  BoxMot's [x1,y1,x2,y2,conf,cls] float32 array.
- `_boxmot_to_sv(np.ndarray) → sv.Detections` — converts BoxMot track output
  [x1,y1,x2,y2,track_id,conf,cls,...] back to sv.Detections with tracker_id set.

**Process per frame (process_all_frames — batch path):**
1. Resize frame to 640×640 with `cv2.INTER_NEAREST` (was INTER_LINEAR, changed for speed).
2. Run player detection model (confidence threshold 0.3).
3. Separate ball detections; pad bounding boxes by 10 px.
4. Run NMS on player detections (threshold 0.5, class_agnostic=False).
5. Track with HybridSort via `_sv_to_boxmot` → `tracker.update(dets, frame)` → `_boxmot_to_sv`.
5. Split by class: players, goalkeepers, referees.
6. Classify player teams using `sports.common.team.TeamClassifier`
   (SiglipEncoder crops → KMeans, bootstrapped over first 100+ frames at stride=30).
7. Assign goalkeeper team by nearest-player proximity (centroid distance).
8. Referees assigned class_id = -1.
9. Run field detection model → estimate homography →
   `sports.common.view.ViewTransformer` maps pixel coords to pitch coords (0–105 m × 0–68 m).
   Field homography cached; refreshed every **30 frames** (was 10, increased for speed).
10. Annotate frame: ellipse per player (team colour: blue/pink/gold), triangle on ball, #ID labels.
11. Write annotated frame to `tracked_output_raw.mp4` via `cv2.VideoWriter` (mp4v codec).
12. Record per-frame CSV row + fire `on_frame(live_rows)` callback for WebSocket minimap.

**Team ID smoothing (post-tracking):**
After all frames, a rolling-majority smooth pass (SWAP_WINDOW=50 frames) corrects
brief team-id flips caused by track-swap occlusions, before the CSV is written.

**After all frames:**
- `out.release()` finalises the mp4v file.
- PyAV re-encodes `tracked_output_raw.mp4` → `tracked_output.mp4` as H.264
  (`crf=23, preset=fast`) with `movflags=faststart` (moov atom at front) for browser seek.
- Deletes the raw temp file.
- Writes `Match_Data_CSV/1_tracking.csv`.

**MJPEG streaming (api_server.py patch):**
`api_server.py` patches `cv2.VideoWriter` with `_StreamingVideoWriter` at runtime.
A `_mjpeg_client_count` counter (protected by `_mjpeg_count_lock`) tracks active `/stream/frames`
consumers. JPEG encoding (quality 60) only occurs when `_mjpeg_client_count > 0`, saving
CPU when nobody is watching. The `/stream/frames` handler increments the counter on entry
and decrements in a `finally` block. Queue maxsize = 60; frames silently dropped on full.

**WebSocket live positions (bidirectional):**
The `/ws` endpoint is now fully bidirectional. The server pushes `{type:"status"}` and
`{type:"positions"}` as before. The client can now also send:
- `{type:"frame", image:"<base64 JPEG>"}` — server decodes, runs `_process_rt_frame()` in
  thread-pool executor, returns `{type:"rt_frame", image:...}` + `{type:"positions", rows:[...]}`.
- `{type:"yt_start", url:"<stream URL>"}` — server resolves the URL using `_resolve_stream_url()`
  (streamlink first, yt-dlp fallback), then starts `_stream_capture_thread` as a daemon thread.
- `{type:"yt_stop"}` — sets `_stream_stop` event; thread exits cleanly.
On WS disconnect, `_stream_stop` is also set to kill any active capture thread.

**RealTimeTracker class (Player_Track.py):**
Active, non-commented class for processing single frames in real-time mode.
- Receives pre-loaded `player_model` and `field_model` from api_server.
- Uses HybridSort with `max_age=5000`, `min_hits=1` (more lenient for live streams).
- Inference resizes frames to 640×640, then scales detections back to original resolution.
- Field homography refreshed every `FIELD_REFRESH_INTERVAL=10` frames; cached otherwise.
- Team classification refreshed every `TEAM_CLASSIFY_INTERVAL=5` frames; fitted after
  accumulating `MIN_CROPS_BEFORE_FIT=80` crops.
- Goalkeeper re-linking: GK pitch-side memory + `GK_MAX_GAP=1000` frame absence tracking (increased from 90 to prevent re-linking failures in longer clips).
- Returns `(annotated_jpeg: bytes, live_rows: list[dict])` per frame.
- Note: The old `RealTimePlayerTracker` class (OC-SORT based) is now fully commented out.

**Output:** `Match_Data_CSV/1_tracking.csv`
Columns: frame, player_id, team_id, role, x, y, pitch_x, pitch_y, confidence

---

**`rerender_video()` function (Player_Track.py):**
A post-pipeline utility that re-annotates the original source video using corrected
`1_tracking.csv` data without re-running detection or tracking. Used after
`/matches/{id}/corrections` modifies player IDs/teams/roles.
- Reads `source_video.mp4` (the raw input saved to each match folder since commit 2c50821).
- Reconstructs bounding boxes from (x, y) columns in the CSV (stored as centre points).
- Draws ellipses (team colour) + labels for players/goalkeepers, triangle for ball.
- Writes `tracked_output_raw.mp4` (mp4v), then PyAV re-encodes to H.264 faststart.
- `on_progress(pct)` callback called every 30 frames (0–100%).
- Called from `/matches/{id}/rerender` via a background thread.

### Phase 2 — Movement Features  (Movement_Features.py)

**Input:** `1_tracking.csv`

**`csv_dir` parameter:** `features(csv_dir='Match_Data_CSV')` — all four pipeline entry-point
functions now accept a `csv_dir` argument so they can operate on a saved match directory
instead of always reading/writing `Match_Data_CSV/`. This enables the `/corrections` endpoint
to re-run phases 2–4 in-place against a saved match folder.

Per player per frame:
- **Distance**: Euclidean distance from previous position (pixels).
- **Speed**: `distance × fps`, capped at 200 px/s.
- **Acceleration**: Δspeed between consecutive frames.
- **Sprint flag**: speed > 75th percentile of that player's rolling speed history.

**Output:** `Match_Data_CSV/1_Movement_Features.csv`
Columns: frame, player_id, team_id, distance, speed, acceleration, is_sprint

---

### Phase 3a — Fatigue Scoring  (Fatigue.py)

**Input:** `1_Movement_Features.csv`

Algorithm (per player):
- Baseline established over first ~30 frames (EMA α=0.2).
- `speed_drop    = max(0, (baseline_speed - current_ema_speed) / baseline_speed)`
- `accel_drop    = max(0, (baseline_accel - current_ema_accel) / baseline_accel)`
- `sprint_drop   = max(0, (baseline_sprint_rate - current_sprint_rate) / baseline_sprint_rate)`
- `fatigue_score = 0.4×speed_drop + 0.3×accel_drop + 0.3×sprint_drop`
- Levels: HIGH ≥ 0.7 | MEDIUM ≥ 0.4 | LOW < 0.4

**Output:** `Match_Data_CSV/1_fatigue_scores.csv`
Columns: player_id, team_id, fatigue_score, fatigue_level, speed_drop, accel_drop, sprint_drop

---

### Phase 3b — Goal Probability  (goal_prob.py)

**Inputs:** `1_tracking.csv`, `1_Movement_Features.csv`

Per player per frame (pitch coordinates):
- `distance_to_goal`: nearest goal centre (0,34) or (105,34); factor = max(0, 1 − dist/35).
- `angle_to_goal`: angle subtended by goal posts; factor = min(angle/45°, 1.0).
- `speed_factor`: min(speed/150, 1.0).
- `defender_factor`: min(nearest_opponent_dist/5m, 1.0).
- `goal_probability = 0.40×dist + 0.30×angle + 0.15×speed + 0.15×defender`

**Output:** `Match_Data_CSV/1_goal_predictions.csv`
Columns: frame, player_id, team_id, distance_to_goal, angle_to_goal, goal_probability

---

### Phase 4 — Match Outcome  (Match_Outcome.py)

**Inputs:** `1_tracking.csv`, `1_goal_predictions.csv`, `1_Movement_Features.csv`

The module contains two components:

**`MatchOutcomeTracker` class** — live/per-frame tracker (for future real-time use):
- Maintains running counts for possession, territory, shots, danger, momentum via deques.
- `process_frame(frame_id, detections, movement_by_player, goal_probabilities)` returns
  a full outcome dict after every frame.
- Shot deduplication: cooldown of 15 frames per player.

**`Match_Outcome()` function** — batch CSV reader (called at end of pipeline):
- Reads the three CSVs directly.
- Normalises `pitch_x` from raw pixel range (1405.4–11780.6) to metres (0–105).
- **Territory**: Team 0 attacking half = pitch_x_m > 52.5; Team 1 = pitch_x_m < 52.5.
- **Momentum**: mean speed of last 20% of match frames (requires `team_id` column in
  `1_Movement_Features.csv`).
- Calls `calculate_match_outcome()` for win probabilities, writes
  `Match_Data_CSV/1_match_predictions.csv`.

**`calculate_match_outcome(possession, shots, territory, momentum, avg_danger)`:**
- `strength = 0.25×shots + 0.25×danger + 0.20×possession + 0.15×territory + 0.15×momentum`
- Sigmoid applied to (strength_0 − strength_1), then normalised to win0 + draw + win1 = 100%.
- Draw probability: `max(0, 0.3 − |diff| × 2)`.

**Output:** `Match_Data_CSV/1_match_predictions.csv`

### Post-Pipeline — Match Archiving  (_save_match in api_server.py)

After Phase 4 completes (or on mid-pipeline cancel), `_save_match(original_name)` is called:
- Creates `Saved_Matches/match_YYYYMMDD_HHMMSS/` directory.
- Copies all five CSVs (that exist) and `tracked_output.mp4` into it.
- **Copies `Test_Data/Testing.mp4` → `source_video.mp4`** (raw input, needed for rerender).
- Derives stats from tracking CSV: total frames, unique player count (excluding referee/ball),
  duration string.
- Writes `meta.json` with fields: id, name, date, saved_at, duration, frames, players.
- Writes an empty `names.json` (`{"players": {}, "teams": {}}`) so the frontend can
  immediately PUT player/team name mappings.

### Post-Match Correction Flow  (PlayerNamingModal → /corrections → /rerender)

After a match is saved, users can correct tracking errors in `PlayerNamingModal`:

**Three correction types (sent to `POST /matches/{id}/corrections`):**
1. `id_merges: [{from: int, to: int}]` — merge a secondary track ID into a primary one.
   The secondary ID's rows are rewritten to the primary ID; team_id is set to the
   primary player's modal team.
2. `team_overrides: {pid_str: team_int}` — force a specific player to a team.
3. `role_overrides: {pid_str: role_str}` — force a player's role to "goalkeeper",
   "player", or "referee".

**Server-side (`/corrections`):**
- Applies all three mutation types to `1_tracking.csv` in the saved match folder.
- Re-runs `features()`, `fatigue()`, `goal_prob()`, `Match_Outcome()` with
  `csv_dir=<match_dir>` so all downstream CSVs are recalculated consistently.

**Video rerender (`POST /matches/{id}/rerender`):**
- Triggered automatically by `PlayerNamingModal` after `/corrections` succeeds.
- Reads `source_video.mp4` and the corrected `1_tracking.csv`.
- Calls `rerender_video()` from `Player_Track.py` in a daemon thread.
- Streams **Server-Sent Events** (`text/event-stream`):
  `{"pct": 0–100}` as each frame is written, then `{"done": true}`.
- Frontend shows a progress bar during rerender; Close button is disabled until done.
- Overwrites `tracked_output.mp4` in the match folder when complete.

**Frontend (PlayerNamingModal):**
- Lifted `teamOverrides` / `roleOverrides` state to parent so `VideoTab` can preview
  corrections live before applying.
- New state: `rerendering`, `renderPct`, `renderError`.
- While rerendering: progress bar shown, "Skip"/"Apply" buttons disabled, backdrop
  click blocked (`onClick` guard checks `!rerendering`).
- `onCorrectionsApplied` callback fires after rerender completes, triggering a full
  results reload in the parent (`MatchResultsClient` / `DemoClient`).

Saved matches are served via `/matches` and `/matches/{id}/*` endpoints, enabling the
**Compare page** to load and compare any two previously processed matches.

---

### Cancel Mid-Pipeline  (api_server.py)

- `POST /cancel` sets `_cancel_event` (a `threading.Event`).
- `player_tracking()` (Phase 1) checks `cancel_event.is_set()` every frame and breaks.
- `_run_pipeline()` checks `_cancel_event.is_set()` after each phase boundary.
- On cancel: `_save_match()` is called immediately, saving all partial outputs produced
  so far; status is set to `{cancelled: True, running: False, match_id: <id>}`.
- Frontend shows a "Pipeline cancelled" card with a link to view the partial match.

## KEY FEATURES

- **Dual input modes**: Upload mode (video file) and Real-time mode (YouTube/Twitch URL).
  Toggled in DemoClient via `inputMode` state ("upload" | "realtime").
- **Stream URL resolution**: `_resolve_stream_url()` in api_server.py tries streamlink
  first (best for live streams), falls back to yt-dlp (better for VODs). Both resolved
  relative to the running Python executable so venv tools are always found.
- **HybridSort tracking**: switched from OCSORTTracker (`trackers` package) to
  `boxmot.trackers.hybridsort.hybridsort.HybridSort` with OSNet Re-ID weights
  (`osnet_x0_25_msmt17.pt`). Uses sparse optical flow (cmc_method='sof') for camera motion
  compensation. BoxMot bridge helpers `_sv_to_boxmot` / `_boxmot_to_sv` translate between
  supervision Detections and BoxMot's numpy array format.
- **Model warmup**: After loading models at startup, a dummy inference is run on each model
  to trigger CUDA JIT compilation. A `_models_ready` flag gates `/run`; `/status` exposes it.
- **MJPEG client-aware encoding**: The `_StreamingVideoWriter` only JPEG-encodes frames when
  at least one `/stream/frames` client is connected (`_mjpeg_client_count > 0`). Saves
  substantial CPU during Phase 1 when nobody is watching the live preview.
- **Bidirectional WebSocket**: `/ws` is now fully bidirectional. Clients can push
  `{type:"frame"}` (webcam/canvas frame for RT processing), `{type:"yt_start"}` (URL stream),
  or `{type:"yt_stop"}`. The WS disconnect handler sets `_stream_stop` to clean up any
  active capture thread.
- **Live MJPEG stream** during Phase 1 (upload mode): frontend parses multipart stream via
  Fetch API, extracts JPEG frames (SOI/EOI markers), renders on `<canvas>` with scrubbing controls.
- **Live pitch minimap** (PitchRadar during Phase 1): receives live player positions via
  WebSocket and renders them on an SVG football pitch in real time.
- **Pitch radar scrubber** (post-pipeline): loads all frames (sampled ≤1500) from
  `/results/tracking/frames`, then syncs player dot positions to the video player timestamp.
- **Rebuilt PitchRadar SVG**: The SVG pitch renderer was rewritten to use the exact
  30-vertex, 21-edge layout from `SoccerPitchConfiguration`, with a fixed `viewBox=1050×680`
  (`preserveAspectRatio="xMidYMid meet"`) so the pitch always has the correct 105:68 aspect
  ratio. Goals are rendered extending beyond the pitch boundary. Player dot sizing scales
  with container width. The `H` prop was removed; the container uses `aspectRatio: "105/68"`.
- **Dynamic video resolution fallback**: `/results/tracking` and `/results/tracking/frames`
  now derive actual video resolution from `df["x"].max()` / `df["y"].max()` instead of
  hard-coding 1920×1080, so fallback pixel→% coordinate conversion is correct for any
  resolution. The `last_frame` lookup also prefers the last frame with valid pitch coords
  for player/goalkeeper roles.
- **Custom video player** (post-pipeline): play/pause, seek bar with timestamps,
  speed (0.25×–2×), ±10s skip buttons, fullscreen.
- **Cancel mid-pipeline**: `POST /cancel` sets a threading.Event; the pipeline checks it
  after every frame (Phase 1) and after each phase. Partial data is archived and
  accessible in the gallery immediately.
- **Team ID smoothing**: rolling-majority pass (50-frame window) over the tracking CSV
  corrects brief team-id flips caused by player occlusion/track-swap artefacts.
- **Player & team naming** (PlayerNamingModal): after a run completes, users can assign
  custom names to any player ID and each team; names are saved to `names.json` in the
  match folder via `PUT /matches/{id}/names` and surfaced in charts/comparisons.
- **Post-match corrections** (PlayerNamingModal): users can also fix tracking errors — merge
  two track IDs into one, force a player's team assignment, or change a player's role. Changes
  are sent to `POST /matches/{id}/corrections` which rewrites `1_tracking.csv` and re-runs
  phases 2–4. The corrected video is then re-rendered from `source_video.mp4` via
  `POST /matches/{id}/rerender` (Server-Sent Events progress bar). Requires `source_video.mp4`
  to exist in the match folder (saved from commit 2c50821 onward).
- **`csv_dir` parameter on pipeline functions**: `features()`, `fatigue()`, `goal_prob()`,
  `Match_Outcome()` all now accept `csv_dir='Match_Data_CSV'` (default) so the `/corrections`
  endpoint can re-run them against any saved match folder.
- **Performance tweaks (commit 2c50821 / batch path)**: field refresh interval increased from
  10 → 30 frames; frame resize now uses `cv2.INTER_NEAREST` instead of `cv2.INTER_LINEAR`;
  team classifier bootstrap crops increased (STRIDE=30 retained, initial crop buffer larger).
- **RealTimeTracker performance**: `half=True` (FP16) enabled for faster GPU inference;
  label text scaled to `text_scale=0.4, text_thickness=1` for cleaner overlay on small renders.
- **Team colour classification** using unsupervised clustering on player jersey crops —
  no pre-labelled data required.
- **Pitch coordinate normalisation**: pixel detections mapped to real-world metres
  (0–105 × 0–68) via homographic projection.
- **Full CSV download**: ZIP of all five output CSVs.
- **Zero-config GPU/CPU fallback**: ONNXRuntime and PyTorch both fall back to CPU
  if CUDA is unavailable. `requirements.txt` defaults to CPU (`inference==1.2.1`,
  `onnxruntime==1.21.1`); GPU packages are commented out.
- **Persistent match storage**: every completed (or cancelled) pipeline run is archived
  under `Saved_Matches/` with a timestamped folder, `meta.json`, and `names.json`.
- **Cross-match comparison** (`/compare` page): loads any two saved matches, renders
  head-to-head stat rows, fatigue bar charts, goal probability timelines, and a verdict card.
- **Movement analytics endpoint** (`/matches/{id}/results/movement`): per-player aggregated
  stats — avg/max speed, total sprints, speed series (sampled ≤60 pts), sprint zones (6 buckets).
- **Mock data fallback**: all demo tab components render static mock data from `lib/mockData.ts`
  when `data` prop is `null` (pre-pipeline state), switching to "● Live Data" badge once real.
- **Model pre-loading**: Roboflow YOLOv8 models loaded once at server startup with JIT warmup,
  not on each pipeline run.
- **FastAPI lifespan**: model loading moved from deprecated `@app.on_event("startup")` to
  `@asynccontextmanager async def _lifespan(app)` (runs model loader in a daemon thread).


## KNOWN ISSUES & CONSTRAINTS

### CUDA / cuDNN initialisation (WSL2-specific)
- **System** `libcudart.so.12` is version 12.0 (stale); cuDNN 9.1 needs 12.1+.
- **Fix**: `api_server.py` top-of-file block uses `ctypes.RTLD_GLOBAL` to preload
  the venv's `libcudart.so.12` (12.1) and then `libcudnn.so.9` before any import,
  so ONNXRuntime finds the correct runtime.
- GPU packages: `inference-gpu==1.2.1`, `onnxruntime-gpu==1.21.1`,
  `nvidia-cuda-runtime-cu12==12.1.105`, `nvidia-cudnn-cu12==9.1.0.70`.

### Video codec
- `avc1` (H.264) codec is **not available** in this OpenCV build.
- Pipeline writes `mp4v` (MPEG-4 Part 2) to a temp file, then PyAV **re-encodes** to
  H.264 faststart (`crf=23, preset=fast`) for browser compatibility.
  This is a full transcode (not just a remux), because mp4v and H.264 are different codecs.
- If PyAV transcode fails, the raw mp4v file is renamed to the final path as fallback.

### numpy version conflict
- `inference-gpu==1.2.1` declares `numpy>=2.0.0` but the environment runs `1.26.4`.
- This is a known soft conflict; the pipeline functions correctly with 1.26.4.

### VideoWriter streaming patch
- `api_server.py` replaces `cv2.VideoWriter` with `_StreamingVideoWriter` at runtime
  (module-level monkey-patch). This must remain in place — any refactor that removes
  `cv2.VideoWriter` from `Player_Track.py` will break the live MJPEG stream.

### MJPEG frame queue
- Queue maxsize = 60 frames. If the browser consumer is slow, frames are silently
  dropped (`queue.Full` exception caught and ignored).
- JPEG encoding is skipped when no `/stream/frames` clients are connected.

### Single-video limitation (upload mode)
- The system processes one video at a time. Concurrent pipeline runs are not supported.
- Input video is always saved as `Test_Data/Testing.mp4` (overwritten on each upload).

### source_video.mp4 only in newer matches
- `POST /matches/{id}/rerender` requires `source_video.mp4` in the match folder.
- Matches saved before commit 2c50821 (2026-04-25) do NOT have this file.
- The endpoint returns HTTP 404 with a helpful message if the file is missing.

### BoxMot / HybridSort dependency
- `boxmot` must be installed separately (not in requirements.txt yet).
- Re-ID weights file `osnet_x0_25_msmt17.pt` must exist at `.model_cache/`; BoxMot
  downloads it automatically on first use if the path is writable.
- The old `trackers` package (`OCSORTTracker`) is no longer used; `RealTimePlayerTracker`
  (the OC-SORT based class) is fully commented out in Player_Track.py.

### Stream resolution (real-time mode)
- Requires `streamlink` and/or `yt-dlp` installed in the same venv as the server.
- Both are resolved relative to `Path(sys.executable).parent` to find venv binaries.
- If both fail, `/ws` sends `{type:"rt_error"}` with the error message.
- Only every other frame is processed to reduce latency (`skip_count % 2 != 0`).

### /results/outcome live recomputation
- The `GET /results/outcome` endpoint calls `_compute_outcome()` which re-reads and
  re-calculates all stats from raw CSVs each time it is called. It does NOT read from
  `1_match_predictions.csv`; it recalculates independently using the same formulas.
  This ensures referees/ball are excluded from the live endpoint even if the CSV includes them.

### WebSocket connection manager thread safety
- `_ws_clients` is a plain list protected by `_ws_lock`. Broadcasts use
  `asyncio.run_coroutine_threadsafe` to schedule sends from the pipeline thread back
  onto the event loop. If a client disconnects mid-broadcast, the exception is silently
  swallowed; the client entry is cleaned up on the next `WebSocketDisconnect`.

### Next.js version
- The project uses Next.js 16.x which has breaking changes from prior versions.
- `matchiq_website/AGENTS.md` warns: read `node_modules/next/dist/docs/` before writing code.

## ASSUMPTIONS & LIMITATIONS

- Input video must be a single continuous match clip (not broadcast with cuts).
- Camera must be relatively static (wide-angle, elevated view) for homography to work.
- Team classification assumes exactly 2 teams with visually distinct jersey colours.
- Goal probability formula is heuristic (weighted linear combination), not a trained model.
- Fatigue scoring uses relative performance drop, not absolute physiological data.
- The field detection model must detect enough keypoints to establish homography;
  if it fails, pitch_x/pitch_y are None and all pitch-coordinate features are skipped.
- Player IDs are HybridSort-local (per-video, not cross-match persistent); the Compare
  page therefore matches players by label string, only showing rows common to both matches.
- `/results/outcome` and `/matches/{id}/results/outcome` recompute stats from raw CSVs
  every call; `1_match_predictions.csv` is written for reference but not read by the API.
- `boxmot` and Re-ID weights (`osnet_x0_25_msmt17.pt`) must be installed/present.
- Real-time stream mode requires `streamlink` and/or `yt-dlp` installed in the venv.
